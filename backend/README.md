# Liftoff Backend Service

The backend of the **Liftoff Graduate Recruitment Portal** is a high-performance web service built with **ASP.NET Core 10.0**. It uses **Clean Architecture**, **CQRS (Command Query Responsibility Segregation)** with **MediatR**, and persists data using **Entity Framework Core** with **PostgreSQL**.

The service manages the candidate ingestion lifecycle, handles background workers, communicates with a Python-based LLM Hiring Agent, and exposes rich metrics and management endpoints to the recruiter dashboard.

---

## Architecture Overview

This project is structured according to **Clean Architecture** guidelines, ensuring decoupling between core business logic and external concerns (like databases, APIs, and AI integrations).

### Dependency Flow

1. **Domain (Core)**: Free of external dependencies. Contains entities, value objects, and domain exceptions.
2. **Application**: Contains use cases, query/command handlers, and interfaces (abstractions). Depends only on Domain.
3. **Infrastructure**: Implements database configurations, repository patterns, and external services (Ollama, Graph API). Depends on Application.
4. **Api (Entry Point)**: Sets up dependency injection, handles HTTP requests/routing, and hosts background workers. Depends on Application and Infrastructure.

## Core Technologies

- **Web Framework**: ASP.NET Core 10.0 Minimal APIs
- **Database Access**: Entity Framework Core 10.0 with [Npgsql](https://github.com/npgsql/efcore.pg)
- **Database Engine**: PostgreSQL 16
- **Mediator Pattern**: MediatR 14.2 (for decoupled CQRS pipelines)
- **API Documentation**: Microsoft OpenAPI + [Scalar ASP.NET Core API Reference](https://github.com/scalar/scalar)
- **Local LLM PDF Classification**: [PdfPig](https://github.com/UglyToad/PdfPig) (PDF text extraction) + Ollama API (`gemma3:4b` / `llama3`)
- **Testing**: xUnit & Microsoft.AspNetCore.Mvc.Testing

## Database Schema Overview

The database contains four primary tables under the `public` schema. The SQL script is available in `./init.sql`.

1. **`ApplicationRecords`**:
   Tracks the primary candidate metadata, current status (`PENDING`, `PROCESSING`, `VALID`, `INVALID`, `MANUAL_REVIEW`, `SHORTLISTED`, `ACCEPTED`, `REJECTED`, `ERROR`), AI-assessed evaluation tier (`STRONG`, `BORDERLINE`, `WEAK`), and recruiter ownership.
2. **`HiringAgentEvaluations`**:
   Stores deep structured JSONB details generated by the AI agent, including institution metadata, score breakdowns (`open_source`, `self_projects`, `technical_skills`), bonus points, deductions, strengths, and candidate summaries.
3. **`RecruiterActions`**:
   Maintains a historic audit trail of actions taken by recruiters (claims, shortlists, status overrides, ratings, and notes).
4. **`AuditLogs`**:
   Records telemetry logs and parsing results across different services.

## API Endpoints

The API is fully documented using OpenAPI. When the service is running in **Development** mode, you can access the interactive **Scalar API Reference** at:
👉 **`http://localhost:5000/scalar/v1`**

### Key Endpoint Groups

#### Ingestion & Evaluation
- `POST /api/applications/ingest` - Receives multi-part form data containing the candidate's details, CV, and optional transcript.
- `POST /internal/evaluation` - Webhook callback endpoint invoked by the LLM Hiring Agent to upload parsing results, scores, and JSON evaluation data.
- `POST /api/applications/{id}/re-evaluate` - Resets and re-triggers LLM evaluation for a candidate.

#### Recruiter Actions
- `POST /api/applications/{id}/ownership/claim` - Recruiter claims review ownership.
- `POST /api/applications/{id}/ownership/shortlist` - Shortlists candidate for the interview phase.
- `POST /api/applications/{id}/ownership/accept` - Transitions status to `ACCEPTED`.
- `POST /api/applications/{id}/ownership/reject` - Transitions status to `REJECTED`.
- `POST /api/applications/{id}/ownership/rate` - Applies a 1-5 star rating and notes.
- `POST /api/applications/{id}/ownership/notes` - Adds recruiter notes to the record.

#### Dashboard & Queries
- `GET /api/dashboard/applications` - Fetches filtered list of candidates (by status, tier, claimed, shortlisted, date).
- `GET /api/dashboard/metrics` - Aggregates recruitment pipeline metrics.
- `GET /api/applications/{id}/cv` - Serves the raw CV PDF file.
- `GET /api/applications/{id}/transcript` - Serves the raw transcript PDF file.
- `GET /api/applications/logs` - Retrieves global recruiter actions timeline log.

## Running the Application Locally

### Using .NET CLI
Ensure you have the .NET 10 SDK installed and PostgreSQL running.

1. **Restore dependencies**:
   ```bash
   dotnet restore
   ```
2. **Start the API**:
   ```bash
   dotnet run --project src/Api/Api.csproj
   ```
   The service will start listening on `http://localhost:5000`.

### Database Auto-Initialization
On application startup, `GradRecruitmentSchemaInitializer` checks and creates the tables if they don't exist. In non-test environments, `DbSeeder` automatically populates default mock profiles so that you can view mock data on the dashboard immediately.

## Docker Integration

To build and run the backend as a standalone Docker container:

```bash
# Build the container
docker build -t liftoff-backend .

# Run the container (ensure PostgreSQL environment variables are configured to route inside the container network)
docker run -p 5000:5000 --env-file .env.development liftoff-backend
```

## Running Integration Tests

Integration tests verify API controllers, CQRS commands, repository constraints, and idempotency key handling without needing a live PostgreSQL database. They utilize an in-memory repository mock.

Run the tests using the .NET CLI:

```bash
dotnet test
```
